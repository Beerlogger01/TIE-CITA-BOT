## Что проверяется автоматически

Тесты используют сохранённые **синтетические HTML-фикстуры**, а не HTML, полученный с государственного портала. Все переходы выполняет настоящий Chromium через Playwright на локальном HTTP-сервере. Отправки запросов на государственный портал во время тестов нет.

| Проверка | Метод |
|---|---|
| Известные первоначальные экраны | Chromium: провинция, процедура, sin Cl@ve, NIE/имя/национальность, Solicitar Cita |
| Промежуточное предупреждение не равно отсутствию мест | Специальное предупреждение на странице заявителя; проверка продолжается до Solicitar Cita |
| Отсутствие мест | Точная испанская фраза после запроса |
| Неизвестный экран | Остановка в AWAITING_USER, активный браузер сохраняется |
| CAPTCHA, блокировка, истечение сессии, ошибка сервера | Раздельная классификация HTML и HTTP статусов |
| Не считать календарь подтверждением | Отдельные проверки классификатора и запрет фиксации без доказательства |
| Подтверждение | Отвергается частичный/неверный номер и дата; принимается явный заголовок и совпадение номера/даты на макете |
| Подтверждённый профиль больше не проверяется | Полный цикл на макете и восстановление по авторитетной таблице bookings |
| Два профиля | Поочерёдное выполнение без двух Chromium для заявителей |
| Одна проверка, один браузер | Конкурентные ручные запросы отвергаются до второго запуска |
| Передача управления в процессе навигации | Задача Playwright отменяется; текущая страница сохраняется |
| Частота | Глобальный минимум 15 минут, включая ручную кнопку, переключение и рестарт |
| Расписание | Europe/Madrid, четверг летом/зимой, опциональное утро, backoff |
| Перезапуск с незавершённой процедурой | SESSION_EXPIRED вместо фиктивного восстановления места |
| Прекращение видимой доступности | Снимается индикатор, пользователь уведомляется, вкладка не обновляется и не закрывается |
| Блокировка после рестарта | BLOCKED сохраняется, автоматического продолжения нет |
| Хранилище | Каталог 0700, SQLite 0600, журнал только с внутренними кодами |
| Исключения/валидация | Ошибки с контрольными секретами не попадают в API или журнал |
| Ingress | Проверяется socket peer; поддельные proxy-заголовки не дают доступа |
| CSRF | Изменения и WebSocket без токена отвергаются до передачи управления |
| Telegram/SMTP | Формат payload, кнопка, список разрешённых получателей, резервный SMTP при ошибке Telegram; доставка замокана |

## Тест «уведомление → другой клиент → та же вкладка»

`tests/test_handoff.py` запускает графический Chromium заявителя и локальный макет. После появления следующего шага проверяет паузу **до** отправки уведомления. Telegram Bot API заменён перехватчиком payload. Другой клиент с отдельным браузерным контекстом открывает путь из URL-кнопки через локальный макет авторизации и Ingress. Неавторизованный клиент получает 401.

После входа клиент открывает noVNC и отправляет клавиши через WebSocket/VNC. Текст появляется в исходной вкладке Chromium заявителя. Проверяются идентичность объектов browser/context/page, неизменность URL и cookies, сохранность JS-маркера документа, одна отправка формы и одна вкладка. После отключения noVNC автоматизация остаётся на паузе.

В этом тесте **два браузера нужны только для моделирования удалённого клиентского устройства**. Внутри работающего add-on заявители обслуживаются одним браузером.

Три варианта размера экрана: desktop, 412×844 и 390×844. Это проверка мобильных размеров в Chromium, **не физические Android/iPhone и не проверка Safari/WebKit**. Авторизация настоящего Home Assistant, запуск из Telegram, особенности мобильных клавиатур и удалённая сеть требуют отдельного приёмочного теста.

## Сборка и платформы

- Нативная amd64 Docker-сборка с закреплёнными Python-зависимостями, соответствующим Playwright Chromium и noVNC выполняется в этой среде.
- Все 17 runtime-зависимостей успешно разрешены и установлены в отдельный каталог как бинарные пакеты **Linux ARM64 / Python 3.12**, с проверкой хешей `requirements.lock`. В локальной среде ARM-код не выполнялся; затем он успешно выполнен в нативном ARM64 CI.
- Локальная попытка ARM64 запуска завершилась `exec format error`: хост x86_64, binfmt/QEMU отсутствует. После публикации PR полная сборка и запуск успешно проверены на нативном ARM64 runner GitHub Actions, включая графический Chromium и noVNC.
- Workflow с нативными `ubuntu-24.04` и `ubuntu-24.04-arm` [выполнен успешно](https://github.com/Beerlogger01/TIE-CITA-BOT/actions/runs/42225980984). На каждой архитектуре реально собраны основной и тестовый образы, выполнены все 39 тестов и `scripts/container_smoke.py`.
- В ходе проверки исправлены права доступа к исходникам в образе после перехода на непривилегированного пользователя. Временные ошибки VFS из-за нехватки диска не являются успешными проверками; соответствующие попытки повторяются после очистки только артефактов этой задачи.

## Что ещё обязательно проверить на оборудовании пользователя

1. Запуск на физическом Pi 4B / HA OS 17.x+, фактические RAM/CPU и длительный мониторинг вместе с Mosquitto/Zigbee2MQTT. Нативная ARM64-сборка и тесты на ARM64 CI уже прошли; подтверждённого профиля потребления ресурсов Pi пока нет.
2. Настоящий Supervisor Ingress: доступ только через вход в HA, правильный slug, HTTP и WebSocket под реальным префиксом. Локальный proxy проверяет контракт, но не заменяет Supervisor.
3. Реальное получение persistent notification, диагностических состояний HA, сообщений Telegram и SMTP. В тестах внешняя доставка замокана; SENT означает принятие канала, не прочтение получателем.
4. Удалённый вход по HTTPS на физическом Android и iPhone, в том числе из другой страны, переход из Telegram, reconnect и экранная клавиатура. Внешние VNC-порты открывать не нужно.
5. Единственную ручную проверку реального портала с профилем владельца: известные локаторы и страницы sin Cl@ve до ответа Solicitar Cita. Автоматического обращения к порталу в этой разработке не было.
6. Реальные последующие страницы выбора офиса/даты/времени, SMS и подтверждения. Для адаптации нужны обезличенные материалы. Совпадение с локальными фикстурами не заявляется как проверенная поддержка этих реальных экранов.
7. Корректность фиксации **реального** подтверждения: номер, дата и заголовок должны распознаваться на действующей странице. Пока проверен только локальный макет. Бот не заявлен как способный автоматически завершать бронирование.

До этих проверок нельзя утверждать, что все критерии готовности из ТЗ выполнены, или что add-on уже испытан на официальном портале. Исходники и установочная конфигурация подготовлены для выполнения этих проверок владельцем; автоматическое окончательное подтверждение отключено.
